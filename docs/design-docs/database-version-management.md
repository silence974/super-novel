# Database Version Management

## 目的

定义 `super-novel` 的正文分层、数据库内建版本管理、恢复、分支和 Git 边界。本文是版本管理领域的详细设计事实源。

## 已确认的基础边界

- 后端使用 Rust 实现。
- 每个作品工程以本地 SQLite 数据库作为主要持久化载体。
- 正文编辑采用稳定文本块、场景和章节三级组织。
- 草稿正文、正式正文和已确认故事事实是三个不同的数据层。
- AI 生成、提取和分析的结果默认是候选结果，不能直接写入正式正文或正式事实。
- Git 不作为核心依赖。普通用户无需安装、理解或操作 Git，也能使用完整版本管理能力。

## 数据层级

```text
Draft Text
  -> 用户提交并确认
Canonical Text
  -> 智能提取并由用户确认
Confirmed Story Facts
```

正式正文不等于正式事实。角色对白、谎言、梦境、幻觉、回忆、猜测和不可靠叙述都可以进入正式正文，但不能因此自动成为故事世界中的正式事实。

最小编辑与确认单位是具有稳定 ID 的 `ContentBlock`。`Scene` 组织有序文本块，`Chapter` 保存可完整恢复的章节正式快照。

## 数据库内建版本管理

### 决策

版本管理由项目数据库内建实现，提供类似 Git 的提交、分支、比较和恢复能力，但其对象是正文、事件、事实、关系和世界状态，而不是文件。

```text
数据库当前工作区
  |- DraftRevision：自动保存的正文草稿
  |- ProjectCommit：用户确认形成的正式项目版本
  |- ProjectBranch：替代剧情或不同结局分支
  |- ProjectSnapshot：加速恢复和保护高风险操作
  `- ObjectRevision：各领域对象的不可变历史版本
```

### 目标

- 可以恢复任意正式版本的正文以及与其一致的世界信息。
- 正文、事实、事件、关系和世界规则在一次提交中保持原子一致。
- 支持不同剧情方向和结局分支。
- 支持把当前正式正文和正式事实压缩为干净的分支基线，用于探索性改动。
- 恢复历史版本时不删除后续历史。
- 能比较两个正式版本或两个分支的领域差异。
- 数据库 schema 升级后仍能识别历史版本。

### 非目标

- 不把每次按键或自动保存都创建为项目级提交。
- 第一阶段不实现自动三方合并。
- 探索快照的历史压缩不删除或改写原分支历史。
- 不允许 AI 自动创建正式提交、切换分支或覆盖历史。
- 不依赖 Git 提供数据库内版本能力。

## 版本层级

### DraftRevision

`DraftRevision` 用于高频自动保存：

- 以 `ContentBlock` 为最小版本单位。
- 不进入正式事实链。
- 不触发项目级分支历史。
- 可以按照保留策略合并或清理中间版本。
- 用户确认前始终属于可变工作区。

### ProjectCommit

`ProjectCommit` 是用户可感知的正式版本。以下操作应创建提交：

- 将草稿正文确认为正式正文。
- 确认、废弃或取代正式事实与事件。
- 应用用户授权的修复补丁。
- 执行历史恢复。
- 创建用户要求的项目里程碑。

一次提交必须在同一个 SQLite 事务中记录：

- 新的正式正文对象版本。
- 新增、修改、取代或废弃的正式事实。
- 事件、关系、世界规则和故事状态变化。
- 用户确认决策与已明确忽略的检查结果。
- 提交父节点和当前分支头。

任何一步失败都必须回滚整个提交，不允许出现“正文已恢复但世界状态仍属于新版本”之类的部分成功。

### ProjectSnapshot

`ProjectSnapshot` 是项目状态的物化快照，用于避免从项目创建开始重放全部变更，也可以作为探索分支的独立基线。

快照类型包括：

- `recovery`：恢复、切换或高风险操作前的安全快照。
- `periodic`：用于缩短历史状态重建路径的周期快照。
- `migration`：数据库 schema 迁移前的完整快照。
- `branch_baseline`：将当前正式状态压缩为探索分支起点的基线快照。

快照应在以下时机生成：

- 用户手动创建快照。
- 数据库迁移前。
- 大规模修复或批量改写前。
- 分支切换或历史恢复前。
- 达到配置的提交数量或数据量阈值时。

Assumption: 快照频率、压缩方式和保留数量需要通过真实长篇作品压力测试确定。

## 核心版本实体

### ProjectCommit

建议字段：

- `id`
- `project_id`
- `branch_id`
- `parent_commit_id`
- `second_parent_commit_id`
- `snapshot_id`
- `squashed_from_commit_id`
- `message`
- `change_type`
- `created_at`
- `schema_version`
- `content_hash`

`second_parent_commit_id` 为未来人工合并保留；第一阶段不实现自动合并。`squashed_from_commit_id` 记录探索快照基线来源，但不把原提交链作为新分支的可见父历史。

### ProjectSnapshot

建议字段：

- `id`
- `project_id`
- `snapshot_type`
- `source_branch_id`
- `source_commit_id`
- `schema_version`
- `manifest_hash`
- `created_at`

快照清单记录目标状态中所有正式对象及其 `ObjectRevision`。清单优先引用已有不可变对象版本并按哈希去重，不为每次探索分支重复复制全部正文和事实。

### ObjectRevision

建议字段：

- `id`
- `object_id`
- `object_type`
- `revision_number`
- `operation`：`create`、`update`、`delete`
- `payload`
- `payload_schema_version`
- `payload_hash`
- `created_at`

可版本化对象包括：

- `content_block`
- `scene`
- `chapter`
- `character`
- `location`
- `item`
- `event`
- `fact`
- `relationship`
- `world_rule`
- `foreshadowing`

`ObjectRevision` 用于不可变历史和恢复，不替代面向业务查询的明确领域表。不能把所有正式数据只存入一个通用 JSON 表。

### CommitChange

建议字段：

- `commit_id`
- `object_id`
- `object_revision_id`
- `change_role`

`CommitChange` 描述一次提交引入的差量。目标提交的完整状态由最近快照与后续提交差量共同解析。

### ProjectBranch

建议字段：

- `id`
- `project_id`
- `name`
- `base_commit_id`
- `head_commit_id`
- `source_branch_id`
- `source_commit_id`
- `history_mode`
- `created_at`
- `archived_at`

第一阶段分支能力包括：

- 从当前提交或历史提交创建分支。
- 从当前正式状态创建压缩历史的探索快照分支。
- 切换分支。
- 比较两个分支。
- 恢复或导出指定分支。
- 归档不再使用的分支。

分支切换前必须保存当前草稿或获得用户明确选择，不能静默丢弃未确认文本。

`history_mode` 第一阶段支持：

- `linked`：新分支保留来源提交作为父历史。
- `squashed_snapshot`：新分支以完整快照作为独立基线，原历史通过来源字段追溯，但不出现在新分支的日常版本列表中。

## 探索快照分支

### 目的

用户可以把当前作品状态冻结为一个新的、历史已经压缩的分支，然后在其中尝试替代剧情、人物命运、世界规则或结局，而不影响原分支。

“之前的变更历史全部合并”定义为逻辑 squash：

- 原分支的提交、正文版本和事实版本继续完整保留。
- 系统为当前正式状态生成 `branch_baseline` 快照。
- 系统创建一个无可见父历史的基线提交，其内容等价于来源提交的完整状态。
- 基线提交通过 `squashed_from_commit_id`、`source_branch_id` 和 `source_commit_id` 保留来源关系。
- 新分支的后续提交只以该基线提交为父节点。

```text
main:        C1 -> C2 -> ... -> C25
                              |
                              `- materialize snapshot S1

experiment: B1(S1) -> E2 -> E3
            B1 的日常历史从此处开始
            B1 可追溯到 main/C25，但不展开 C1..C25
```

### 创建流程

创建探索快照分支必须在单个受控操作中完成：

```text
暂停正式写入
  -> 保存当前草稿
  -> 检查未确认正文和候选事实
  -> 解析当前分支正式提交的完整状态
  -> 创建 branch_baseline ProjectSnapshot
  -> 创建 squash 基线 ProjectCommit
  -> 创建 ProjectBranch 并设置 base/head
  -> 校验快照和对象哈希
  -> 可选切换到新分支
  -> 恢复正式写入
```

若存在未确认草稿，系统不得把它静默提升为正式正文。用户必须选择：

- 先完成确认，再创建探索分支。
- 只以当前正式状态创建分支，并把草稿作为新分支的非正式 `DraftRevision` 副本。
- 取消创建。

候选事实、未应用补丁和未确认分析结果默认不进入正式快照；它们可以作为分支级工作资料复制，但仍保持候选状态。

### 采用探索结果

探索分支不能自动覆盖来源分支。系统应比较探索分支头与其 `branch_baseline`，生成领域级候选变更集：

- 正文变更。
- 新增、修改或废弃的事实。
- 事件与关系变化。
- 世界规则变化。
- 受影响范围和冲突检查结果。

用户可以选择全部或部分变更，在目标分支创建新的 `ProjectCommit`。该操作属于用户授权的变更应用，不属于自动三方合并。

### 删除与归档

删除或归档探索分支不得删除仍被原分支、其他分支、快照或提交引用的对象版本。物理空间回收必须在引用可达性检查后单独执行。

## 正式化与版本提交工作流

```text
编辑 ContentBlock
  -> 自动保存 DraftRevision
  -> 用户提交确认
  -> 冻结待确认草稿
  -> 对候选正文执行事实提取和冲突预检查
  -> 用户确认正文或明确忽略问题
  -> 创建 Canonical Text 的 ObjectRevision
  -> 提取 Candidate Fact / Candidate Event
  -> 用户确认候选事实
  -> 在单个事务中创建 ProjectCommit
  -> 更新正式领域表
  -> 重建受影响的派生状态和索引
```

`error` 级冲突需要用户显式确认后才能继续；`warning` 和 `notice` 不阻断正式化。冲突确认本身必须进入提交记录。

## 恢复规则

恢复历史版本不得删除当前版本及其后续历史。

支持两种恢复方式：

### 恢复为新版本

从目标提交解析正文和正式故事状态，在当前分支创建一个内容等价的新提交。该操作类似 revert，保留当前完整历史。

```text
C25 -> C26
       C26 的领域状态与 C17 等价
```

### 从历史创建分支

以目标提交作为新分支的起点，用于不同剧情方向、不同角色命运或不同结局。

```text
C17 -> branch/dark-ending
```

任何恢复操作前都必须创建安全快照。恢复失败时应继续保持原分支头和数据库状态。

## 故事状态与派生数据

正式事实、事件、关系和世界规则必须参与版本管理。以下数据属于可重建的派生数据：

- 当前人物状态投影。
- 图查询缓存。
- 全文检索索引。
- 向量索引。
- 分析结果索引。
- 章节和项目统计。

切换、恢复或重建历史版本后，派生数据按照目标提交的正式事实重新计算。分析结果必须记录其输入 `commit_id`；当前提交变化后，旧分析结果应标记为过期，不能继续当作当前结论。

## 完整性与空间控制

- 每个对象版本和项目提交必须具有内容哈希，用于检测损坏和不完整恢复。
- 历史对象版本采用不可变写入，禁止原地覆盖。
- 正式提交不允许被自动清理。
- 草稿自动保存可以按照保留策略压缩，但必须保留最近版本和用户标记版本。
- 大文本按 `ContentBlock` 保存版本，避免每次修改都复制整本小说。
- 相同内容可以按哈希去重；具体压缩算法属于实现决策，不在领域层固定。
- 数据库文件损坏或丢失会同时影响当前数据和内部历史，因此必须提供独立的项目备份机制。

## Git 的定位

Git 不是版本管理事实源，也不是运行依赖。项目在没有 Git、Git CLI 或网络的环境中必须能够完整使用：

- 正文版本历史。
- 世界状态恢复。
- 分支和版本比较。
- 项目快照与回滚。

未来可以提供可选 Git 集成，用于将 Markdown、JSON 等可读导出物提交到外部仓库。Git commit 与数据库提交可以建立映射，但 Git 不得覆盖数据库版本语义，也不得自动提交、切换分支或推送远端。

## Open Questions

- 项目快照采用 SQLite Online Backup、序列化领域快照还是混合方式，需要可靠性 spike。
- 大型项目的快照间隔、历史压缩和内容去重阈值需要压力测试。
- 分支差异的领域展示格式需要在后端差异模型确定后再设计前端。
- 历史 payload 跨 schema 版本的迁移与读取策略需要单独设计。
